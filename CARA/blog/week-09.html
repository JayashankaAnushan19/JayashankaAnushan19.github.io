Full Integration Test Finds RFID & Motor Issues, Perception Pipeline Scaffolding Begins

A full-system integration sketch brought every chassis module — bar GSM and the drive motors — onto one board for the first time, immediately surfacing an unresponsive RFID reader and underpowered drive motors. In parallel, the cara_jetson ROS2 package grew from last week's placeholder into a real camera-capture, two-tier patient-tracking, and enrollment pipeline.

Full System Integration Test (15th in the Series)

Every module wired onto the actual assembled chassis — except GSM and the drive motors — was brought together into one sketch for the first time, to catch the kind of integration issue that standalone module tests (9th–13th) can't reveal: a shared I2C bus, SPI timing conflicts, pin conflicts, or combined power draw problems.

Included: buzzer, I2C LCD, RFID access control, 4×4 keypad, 2× PIR, DS18B20 temperature, DS3231 RTC, and the 6× HC-SR04 ultrasonic ring (sensing/logging only). Deliberately excluded: GSM stays out per the current plan, and the drive motors are declared in the pin map for documentation but never actuated — the current motors don't have enough torque at low PWM and are being replaced (see below). This is a new file; cara_main_mega.ino itself was not touched, per the standing rule of never editing the real firmware directly.

Two things were added that hadn't been tested before: a hardcoded one-shot medication-reminder alert two minutes after boot (buzzer + LCD prompt, acknowledged with the keypad's *), as a first check that the alert mechanism itself works before building a real keypad-driven schedule UI around it — and RTC time correction over serial, so the DS3231 clock can be set without a recompile.

RFID Comes Back Unresponsive — Diagnosed at the Wiring Level

The RFID reader kept reading VersionReg = 0x00 through the MFRC522 library during the integration test — which only says "not responding," with no detail on why. A dedicated diagnostic sketch was built to bypass the library entirely and bit-bang the SPI protocol by hand, printing every bit that comes back on MISO:

  • MISO never changes across all 8 bits → that line is dead/disconnected, or the chip has no power / isn't responding at all.
  • MISO changes but the result still isn't a real value → communication is happening at the pin level, so the fault is elsewhere (RST line, timing, or a damaged chip).
  • A real value (0x91/0x92) suddenly comes back → the pins are actually fine, and the library-based test may have hit a transient/init issue worth re-confirming.
  • As an extra cross-check, the same wiring was also swapped onto otherwise-unused Mega pins and re-tested on a separate Uno rig, to rule out the specific SPI pins (53/52/51/50/49) themselves being damaged.

Obstacle Avoidance Retuned ("Gentle Walker" v2)

The obstacle-avoidance sketch was revised based on real bench-test feedback from the first version, which was triggering "blocked" almost everywhere in a normal room and stalling out at the chosen motor speed:

Parameterv1v2Why
STOP_DIST60 cm12 cmv1 flagged "blocked" almost everywhere in a normal room
MOTOR_SPEED15070Motors have a minimum PWM floor below which they stall — needs re-tuning once the motors are replaced

There's no true PID controller here — that needs a feedback sensor (wheel encoders or a gyro) that isn't wired in yet. What smooths the motion instead is open-loop ramping: speed changes gradually over a few hundred milliseconds rather than jumping instantly, which is what actually produces calm, non-startling movement for a companion robot meant to move around elderly users. A small tie-breaker was also added so the left/right turn choice doesn't flip-flop forever when both sides look equally blocked, plus a standalone live_proximity_view.py tool for watching the sensor ring in real time on a laptop.

Perception Pipeline: the cara_jetson ROS2 Package Grows

Last week's placeholder scaffold turned into real nodes: camera_node captures webcam frames and publishes them as ROS2 Image messages on /cara/camera/image_raw at 15 fps — the one piece of the pipeline with zero dependency on the Arduino link. person_tracker_node keeps a continuous lock on the patient using two cooperating tiers: face detection first, falling back after a few consecutive missed frames to color-blob detection of a bright, highly-saturated wristband that's chosen specifically to still segment well in low light. While band-locked, face detection keeps retrying inside a region of interest expanded around the band's position, so the band anchors quick re-acquisition of the face instead of losing the patient outright — states are FACE, BAND, or LOST, published for downstream nodes (motion control, fall detection) to hold position on rather than guess.

A companion enroll_patient_node is a keyboard-driven admin tool — capture a photo with C, train the recognition model with T, reset with R, quit with Q — that writes to disk so enrollment survives a reboot and only needs doing once per patient. fall_detection_node is still a placeholder that just confirms the package builds and runs end-to-end; per the standing rule of never editing the existing main scripts directly, it will eventually wrap the real logic in Skeleton_Analysis/fall_detection.py rather than duplicate it.

Also This Week

A smaller fix landed alongside the above: remote_control.py was using a hardcoded test-video file instead of the live webcam by default — now fixed to use the actual camera.

What Did Not Go Well

The drive motors are now confirmed inadequate rather than just suspected — the obstacle-avoidance retune can't be properly validated on real hardware until they're replaced. The RFID diagnostic sketch is built, but it hasn't been run against real hardware yet to get a conclusive read on which of the three failure modes this actually is. GSM SMS-send / network-registration testing, open since Week 06, still hasn't been picked back up.
