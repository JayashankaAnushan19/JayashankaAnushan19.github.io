14–20 Aug 2026 Week 10 Hardware Software Complete

Remote Control Hardened, and the RFID Mystery from Week 09 Finally Solved

remote_control.py was made robust enough to run unattended as a systemd service — real network-interface enumeration instead of a single guessed IP, and auto-reconnecting camera/serial links. Later in the week, raw pin testing found the Mega's hardware I2C pin physically damaged, fixed with a hand-written bit-banged LCD driver — and while chasing that, the RFID module was swapped and finally confirmed working, closing the question left open at the end of Week 09.

remote_control.py Hardened for Always-On systemd Service

Two reliability gaps mattered now that this script runs as an always-on systemd service rather than something started by hand: how it finds its own IP, and what happens when the camera or Arduino isn't available yet.

IP detection previously used socket.gethostbyname(gethostname()), which guesses a single IP and is unreliable on this dual-NIC machine. It's now replaced with real interface enumeration via ip -4 -o addr show, filtering out loopback/docker/virtual interfaces, and prints all live IPs (Wi-Fi and Ethernet) at startup — no more guessing which one to actually use.

Camera and serial connections previously connected once at startup and gave up permanently if unavailable. As a systemd service, the Arduino or camera may not be plugged in yet when the service starts, or may get unplugged and replugged later — so both now auto-reconnect instead of failing for good.

Groundwork for an On-Demand IP Display

On every serial (re)connect, remote_control.py now sends a SET_IPS command to the Arduino with the current IP(s). cara_main_mega.ino doesn't act on this yet — it's currently ignored by handleCommand() — so this is groundwork only. Acting on it for real needs a new sketch (not an edit to the real firmware) and real hardware to build and test against, tracked as a separate follow-up.

Reference Notes: a Second LCD Wired Directly to the Jetson

There are now two separate, unrelated ideas for showing the IP on an LCD, worth keeping distinct so they don't get conflated:

  1. The Arduino's existing 16×2 LCD, driven by the SET_IPS serial command above — not built yet.
  2. A second, separate LCD wired straight to the Jetson's own I2C pins, with no Arduino involved at all — this is the one that could stay on-screen permanently, since it isn't competing with the Arduino LCD's state-machine, greeting, and alert messages.

Notes-only for now — nothing is wired or installed. The same PCF8574-backpack-style 16×2 I2C LCD already used on the Arduino side would work here too, since it's a standard I2C peripheral with nothing Arduino-specific about it.

The bus number needed on-device confirmation rather than a guess: checking this Jetson's available I2C adapters points to /dev/i2c-7 (c250000.i2c) as the most likely match for the 40-pin header's I2C — flagged as a candidate, not yet confirmed, until real hardware is attached and tested.

LCD Diagnosed and Fixed — Hardware I2C Pin Was Damaged

Raw pin testing on the Mega found the hardware SCL line (pin 21) stuck permanently low — physically damaged, not a wiring or code problem. Since the standard Wire library can't be moved off pins 20/21, the fix was a hand-written, bit-banged I2C+PCF8574+HD44780 driver running instead on SDA=20 / SCL=A0, defined inline in each sketch so it needs no separate library install. The DS3231 RTC still shares the old, damaged bus and stays disabled for now — that's tracked as a separate follow-up, not solved by this fix.

cara_main_mega.ino, cara_main_mega_gsm.ino, TenthTest_LCDCheck, and FifteenthTest_FullIntegration were all updated to the new driver. Two new test sketches came out of the bring-up: LCDCheck_RotatingContent (rotating greeting + live clock) and SixteenthTest_LCD_RFID_Buzzer_Keypad, a combined module test.

RFID Module Replaced and Confirmed Working

While chasing the LCD issue, the RFID reader from Week 09 got resolved too: swapping in a new module fixed the VersionReg = 0x00 mystery outright — the new one reads back 0x92 (a genuine chip) and correctly reads and distinguishes tags. A KnownTags.md reference list of scanned UIDs was added alongside it, so tag identities don't have to be re-derived from scratch each time.

What Did Not Go Well

Two items carried over stay open: the Arduino side of SET_IPS still isn't implemented, and the drive motors still need replacing. The RTC is now a newly-opened item too — deliberately left disabled on the damaged bus rather than fixed alongside the LCD.
