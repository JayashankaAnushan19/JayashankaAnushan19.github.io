4–10 Sep 2026 Week 13 Hardware Software In Progress

From Finishing Covers to a Shared-Power Fault — Root Cause Found, Fix Underway

The week started as a CAD-only stretch — covers and holders that turn a working prototype into something that looks like a finished product. Then a camera-tilt bench test, meant to be routine, uncovered something much more serious: obstacle sensors silently failing open, an RFID reader gone unresponsive, and a servo that still wouldn't move with everything attached — three separate symptoms that traced back to one shared root cause on the Arduino's own power rail. A new browser-based diagnostics tool came out of chasing it down, and a first fix attempt didn't work — but the real fix is now understood and underway. Later in the week: a report accuracy pass, a supervisor meeting with real actionable outcomes, the LaTeX report reframed as a standalone paper with its bibliography rebuilt from real Word citation data, and a proper HSV calibration tool built for the long-open wristband color placeholder.

This week is still in progress. This post reflects the work done so far; more will be added as the rest of the week happens.

Camera Tilt Bench Test — and a More Serious Issue Found Along the Way

Debugging the still-unmoving tilt servo from Week 12 started with a minimal servo-only bench test (NineteenthTest_CameraTiltCheck.ino) — still no movement, which at least ruled firmware out. That was replaced with a proven 3-phase diagnostic (small moves, full sweep, fast snaps) which confirmed the servo works correctly in isolation, and is being kept as the reference for any future tilt debugging.

Re-verifying through the real firmware turned up something more serious: 5 of the 6 ultrasonic sensors (FL/FR/BR/L/R) stuck reporting 0.00, with the tilt servo still not physically moving once everything was attached together. A 0 reading means "no obstacle" in this firmware — it fails open, so obstacle safety cannot be trusted for live movement until this is fixed.

Diagnosis: the shared Arduino 5V rail can't supply enough current once the servo, the full ultrasonic ring, and everything else are all actually attached at once — the same pattern behind the LCD and motor power problems from earlier weeks. The fix is hardware, not yet done. No further live movement tests until this is physically fixed and re-verified.

RFID Isolation Test Confirms the Same Root Cause

A physical test of RFID-acknowledge during a real alert got no response at all — not even an "unknown tag" rejection. An isolated bench test (TwentiethTest_RFIDCheck.ino, same philosophy as the tilt test) found the MFRC522's VersionReg reads back 0x24 — the chip is alive and responding over SPI — but a tag scan produces nothing at all, even with no time limit.

That's a third data point for the same root cause already suspected for the tilt servo and ultrasonic ring: basic digital SPI communication works fine, but actively driving an RF field to detect a tag needs more current than the shared, insufficient power rail can supply. The recommendation going forward is to fix the shared power problem first, before separately debugging RFID wiring — it likely resolves all three symptoms at once.

A Browser-Based Hardware Diagnostics Tool

Chasing all of this by hand — flashing sketches and watching serial output — kept hitting the same friction, so a proper tool came out of it: hardware_diagnostics.py (port 5050), a browser-based flash-and-monitor for the bench-test sketches with no command line or arduino-cli knowledge needed. It scans Sensor_Testing_Codes/After_Full_Assembly for available sketches (plus a pinned entry for the real firmware), a Flash button runs compile-and-upload via arduino-cli, live log streams over Server-Sent Events (the same pattern already used for the camera feed), and a send-command box allows interactive testing — since refined with a preset dropdown (MOVE_FORWARD, TILT_UP, SET_SPEED:200, etc.) that auto-fills but stays editable, with the input left in place after sending so a command can be resent or tweaked quickly.

It also solves a recurring bit of friction from every hardware test this session: manually stopping and starting the cara-remote-control service before and after each bench test. Stop/Start buttons attempt this via non-interactive sudo, with a clear one-time visudo setup command if not yet configured — the same safe pattern already used for the clock-adjust feature, not a raw edit into /etc/sudoers.d/. Live-tested end to end: sketch listing, flash-then-auto-monitor, live streaming, and send-command all confirmed working.

Power Fix Attempt #1 Didn't Help — Real Root Cause Now Understood

The first attempt at a fix — connecting external power to the Arduino board itself, rather than feeding peripherals directly — didn't help. Re-tested via the new diagnostics tool, RFID still detected nothing.

The real root cause: the Arduino's onboard 5V regulator has its own current limit, regardless of how well-powered the board's input supply is — and RFID, the servo, and the ultrasonic sensors are all still wired through that same pin. The agreed real fix, not yet done: external 5V wired directly to each peripheral's VCC, bypassing the Arduino's 5V pin entirely, with a common ground tied back to the Arduino — explicitly not the big drive motors, which already have their own separate supply. That wiring is in progress, to be retested together next session.

Report Accuracy Pass — Diagrams, Text Cleanup, and a Research Questions Section

An ongoing accuracy pass across the week added a full "Research Questions Revisited" section to Chapter 6, redrew Figure 3-2 (Software Architecture) to remove the fictional pan-tilt dual-servo mechanism and collapse the two-ring ultrasonic layout down to the real single 6-sensor ring, and cleaned up several leftover text issues: a stray personal note that had been typed directly into the "Future Work" heading, a duplicated research question, and redundant restated-question openings in the RQ answers.

Supervisor Meeting — Turning Refinement, a Cell-Recovery Attempt, and Real-World Validation

A supervisor progress meeting produced several concrete outcomes. The dissertation should explicitly answer its research questions — matching the new Chapter 6 section above. A motor-control refinement was proposed for the drive motors' known lack of closed-loop feedback: asymmetric left/right power during turns (one side slower, one side faster) instead of equal-and-opposite pivoting, to reduce turn overshoot without needing encoders — not yet implemented, added to Future Work in both report versions.

Also discussed: attempting to recover the dead 3rd LiPo cell — reading 0.01V — by connecting it to a charger in isolation from the rest of the pack. Attempted the same day; the outcome isn't known yet. Real-world/outdoor validation of the fall-detection model specifically (lighting and environment robustness, beyond the current lab-only testing) was requested too, worded carefully in Future Work to apply to the perception model without contradicting the project's declared out-of-scope status for outdoor robot navigation. Separately: the university lab has started 3D-printing the redesigned chassis parts submitted earlier this week, to be installed once received.

LaTeX Report Reframed as a Standalone Paper, Bibliography Rebuilt Properly

The LaTeX report was brought up to date with the same hardware findings as the Word version — the servo named explicitly as MG90S throughout, and the full power architecture (3S 11.1V/7000mAh battery, 5V/6.6V buck rails, a boosted-and-fused 19V rail for the Jetson) added as new hardware-table rows and a paragraph, having been entirely absent from the condensed version.

Per explicit instruction, the document was reframed as a standalone publishable research paper rather than a dissertation excerpt: "dissertation" became "paper" throughout, a formal Research Questions list and an itemised Contributions statement were added to the Introduction, a "Research Questions Revisited" paragraph and a Code/Data Availability statement (linking the GitHub repo) were added to the Conclusion, and Related Work was fully rewritten into 9 subsections matching the dissertation's real literature-review structure — so all real sources are genuinely cited in support of specific claims, not just listed.

The bibliography itself got rebuilt from scratch, properly this time: the Word thesis's in-text citations turned out to be real Word citation-manager fields — 51 CITATION fields and one BIBLIOGRAPHY field — that had simply never been refreshed (Ctrl+A → F9), with Word storing the full real source data for all of them inside the .docx file itself (customXml/item1.xml). All 53 real sources were extracted directly from that XML (51 after merging two true duplicates), replacing the earlier placeholder 7-entry references.bib outright.

Three real data-quality bugs found along the way: a narrow no-break space (Unicode U+202F) hidden inside one title that silently killed the entire pdfLaTeX compile with no PDF produced at all; a trailing comma on a corporate author name ("World_Bank,") that crashed BibTeX outright; and two entries where a long author list had been truncated with a literal "..." or "et al." typed in as a fake extra author, now correctly converted to BibTeX's own "others" convention so it renders as a proper "et al."

Confirmed clean throughout: zero BibTeX warnings, zero undefined citations, final page count 6 — still comfortably within the 8-page cap.

A Proper HSV Calibration Tool for the Wristband

The wristband color has been a known placeholder since Week 11 — bright magenta/pink, never tuned against a real physical band. That finally has a real path forward: hsv_band_calibrator.py, a standalone, laptop-side tool (no dependency on any other project file) for calibrating the actual printed wristband's HSV range under real lighting, before touching any Jetson tracking code. Iterated per feedback into its final form — two live windows (raw camera feed and the filtered/mask preview) instead of three, a clickable on-screen SAVE button plus an 's' keyboard fallback (real GUI buttons aren't reliably supported by standard opencv-python builds), and each save producing one combined image — both views plus the exact H/S/V values as text — into a dedicated captures folder, alongside a running paste-ready text file with the latest values. Set up to be run on the user's own laptop the next day with the now-printed band.

What Did Not Go Well (So Far)

The camera-tilt debugging session uncovered a real safety-relevant issue rather than a simple fix: 5 of 6 ultrasonic sensors currently read 0.00, which this firmware treats as "no obstacle" — obstacle safety cannot be trusted for live movement until the shared-power fix is done and re-verified. RFID remains completely unresponsive to tag scans. The camera tilt servo still isn't confirmed physically moving with everything attached, even though it works correctly in isolation. The first power-fix attempt (external power to the board) didn't resolve anything — the real fix (direct-to-peripheral wiring) is in progress but not yet retested. The dead 3rd LiPo cell's recovery attempt has an unknown outcome so far. The wristband calibration tool is built but hasn't actually been run against the real printed band yet. Everything else carried in from Week 12 is still open too: RFID/keypad reminder acknowledge is untested, turning remains parked as an accepted motor-torque limit, and the isConnected() LCD diagnostic still disagrees with the display's real state. On the hardware-finishing side, every cover and holder designed this week is still just a design file — none printed or test-fitted yet, though the university lab has now started printing them.
