28 Aug–3 Sep 2026 Week 12 Planning Hardware Software In Progress

From Report Audit to a Big Engineering Day — LCD Fixed, Obstacle Fusion Built, Pipeline Verified Live

The week started with a break from firmware and ROS2: the Thesis Report document got a full structural read to find what's genuinely missing versus just out of date, followed by a full LaTeX rebuild of the dissertation, converted to IEEEtran format and re-scoped into a verified 4-page submission document. Then the engineering work came roaring back — the long-open LCD power issue got resolved, the obstacle-detection sensor-fusion idea from Week 11 actually got built, a recognition-threshold bug got fixed, the full autonomous pipeline was verified live end to end including the turn itself, and the "robot isn't moving" mystery was finally root-caused to a dead battery. This post is still in progress and will be filled in further as the week continues.

What the Structural Read Found

Every heading level of the Thesis Report was reviewed to separate three genuinely different problems that "the report isn't finished" can mean:

  • Completely empty sections — Chapter 5's System Integration Evaluation, Objectives Achievement, and Limitations and Threats to Validity; all of Chapter 6; all six appendices, A through F.
  • False alarms — two sections in Chapter 4 still marked ***draft that, on closer read, turned out to already be complete. A labeling leftover, not a real gap.
  • Sections that are filled but now factually behind the actual project — Hardware Implementation's I2C-bus description (predates the bit-banged LCD driver fix), GSM Integration ending on "procured" rather than describing the SMS system now confirmed working, Individual Feature Results covering only 2 of the 15 features, and Phase 1's exclusion list still claiming GSM and live fall-detection weren't done — both now are.

Splitting the problem this way matters because each category needs a different fix: the false alarms just need their draft flag removed, the stale sections need updating to match reality rather than being rewritten from scratch, and the empty sections need real content written for the first time.

A Draft-Fill Reference Guide, Grounded in the Real Project History

For every gap found, a reference page (thesis_fill_guide.html — a local scratch file, not part of this repo) was put together with copy-paste-ready draft text for each section, written to match the report's existing academic tone rather than as placeholder filler. Grounded in what actually happened on this project: the RFID and LCD hardware-fault diagnoses, the SIM800L-to-A76xx GSM migration, motor torque sizing, the person-tracker/fall-detection lock-state gating, and keypad-plus-web patient enrollment — the same history this blog has been tracking week by week.

Deliberately left for the user to write personally, not drafted: the Ethics Approval appendix, the Final Reflection section, and the wiring-diagram appendix — these need to be the author's own material, not generated on their behalf.

A Full LaTeX Version of the Dissertation

A parallel LaTeX build of the whole dissertation went in under reports/LaTex Report/, mirroring the folder layout of an earlier coursework report (main.tex + sections/ + code/ + images/ + references.bib). Every section was populated from the real, freshly re-extracted Thesis Report content — every paragraph and all 7 tables — not placeholder text.

The whole document was then converted to \documentclass[journal,twocolumn]{IEEEtran} (originally a chapter-based report class), which meant shifting every heading level down one and fixing every "Chapter X" reference to "Section X" across all six section files. Getting IEEEtran's twocolumn layout to actually compile surfaced four separate issues: a MiKTeX font-expansion error (fixed by disabling microtype expansion), Unicode characters inside code listings breaking pdfLaTeX (fixed with a literate table), a wide table refusing to run in twocolumn mode (fixed by wrapping it in \onecolumn/\twocolumn), and \appendix (singular) silently dropping three of six appendices — the fix was the plural \appendices. The Declaration of Originality, Acknowledgements, Table of Contents, and all six appendices were then removed from this LaTeX version entirely, leaving Title/Abstract plus six numbered sections.

Re-Scoped to an 8-Page Submission Document

The same LaTeX report was then trimmed down to an 8-page-max submission: System Design and Implementation merged into one section, Related Work condensed to about four paragraphs plus one comparison table, and references.bib cut down to the 7 citations that could actually be verified as real — every placeholder citation dropped rather than left in. Two real figure slots were added (images/cara_robot.jpg, images/test_setup.jpg) that render automatically the moment those files exist — boxed placeholders until then, no `.tex` edit needed once the photos are dropped in.

Verified, not assumed: the true compiled page count was read directly from pdfLaTeX's own log line — an earlier log-grepping check had silently matched the wrong "page marker" text from an unrelated table-overflow warning. The real count: 4 pages, well inside the 8-page cap.

Docx Progress Check and a Corrected Power Diagram

The user's own edits to the Word version of the report were reviewed — the earlier fill-guide content for Chapter 5, Chapter 6, and the Chapter 4 corrections had already been pasted in. Checking which figures are genuinely embedded images (rather than just captions) confirmed Figures 3-1 and 3-2 are real, and re-catalogued what's still empty: the Physical Design section and all six appendices.

The power-system diagram above was built for that Physical Design section, alongside matching report prose — and corrected mid-session after it came out that the Jetson actually runs on 19V through a boost converter with a 2A fuse (wired by the user), not 5V as first assumed. The diagram's Jetson branch was relabeled from a flagged "buck, needs verification" box to the correct 19V boost path with the fuse drawn in. One FYI flagged, not treated as a blocker: that 2A fuse sits under the Jetson power adapter's rated 2.37A draw. Separately, a paragraph already pasted into the docx's Power System Design section turned out to be the pre-correction version — still describing "5V... 4A" — flagged for replacement, along with a garbled figure caption/number that needs a field refresh.

The LCD Mystery, Mostly Resolved — a Real Power Fix

The dark-LCD investigation from Week 11 ended with a physical fix: the whole robot now runs on unified single-battery power instead of the mixed external/converter setup that made the earlier tests hard to interpret, and the LCD is confirmed visually working again. It's not a fully closed loop, though — a settling delay was added to the isConnected() I2C ACK diagnostic to test a timing hypothesis for why it disagreed with the direct visual confirmation the display was working, and that disagreement did not get resolved. Documented honestly as still-unresolved rather than claimed fixed just because the display itself is working.

Obstacle-Detection Sensor Fusion, Actually Built

The diagonal-sensor idea designed but deliberately left unbuilt in Week 11 is real code now. frontBlocked()/backBlocked() replace the old flat "is either corner sensor close?" checks, cross-referencing each corner sensor's sin(45°)/cos(45°)-decomposed side-component against the true L/R sensors — exactly the sensor-fusion approach discussed but not built last week, now distinguishing "this is really a side wall" from "this is genuinely something ahead or behind," which a raw diagonal reading alone can't do. HARD_STOP_DIST (15cm) sits underneath as an unconditional safety floor — always blocks that close regardless of how the fusion interprets it, no exceptions. The fusion result was also added to the live status line for visibility while testing.

Full Autonomous Pipeline Verified Live — Including the Turn Itself

Getting there needed one more bug fixed first: the LBPH recognition confidence threshold was raised from 70 to 85 after live testing found a clean, correct face match scoring 78.66 — just above the old threshold, causing a false LOST/no-match on a genuinely good detection. It turned out to be a duplicate bug across two independent recognizer instances, since the ROS2 node and the web UI each keep their own.

With that fixed, the full autonomous tracking pipeline was live-verified end to end for real this time: real SET_SPEED/TURN_LEFT commands with correct proportional-speed deceleration actually reaching the Arduino — the "watched it turn to recenter" moment that's been open since Week 11 finally happened. A new standalone tool, wasd_web_control.py (a Flask WASD control page on port 5003), came out of this too, for bench-testing the L298N motor driver in isolation from the rest of the stack.

The "Robot Isn't Moving" Mystery — a Dead Battery

The long-open "robot not moving, no sound at all" report from Week 11 finally got root-caused: a dead battery, not a wiring or driver fault. Confirmed via an isolated bench test using the new WASD tool above, then cara_main_jetson.ino was re-flashed and re-verified back on the Arduino afterward.

What Did Not Go Well (So Far)

The isConnected() I2C diagnostic still disagrees with the LCD's actual working state — a real, unresolved inconsistency, not swept aside just because the display itself is fine now. The physical wristband still hasn't been built, person_tracker_node still needs a restart to pick up a freshly trained model, and remote_control.py still isn't migrated onto /cara/drive_cmd. On the report side, the docx still has a stale pre-correction power paragraph sitting in it that needs manually replacing, and the Physical Design section plus all six appendices remain unwritten.
