28 Aug–3 Sep 2026 Week 12 Planning Hardware Software In Progress

From Report Audit to a Big Engineering Day — LCD Fixed, Obstacle Fusion Built, Pipeline Verified Live

The week started with a break from firmware and ROS2: the Thesis Report document got a full structural read to find what's genuinely missing versus just out of date, followed by a full LaTeX rebuild of the dissertation, converted to IEEEtran format and re-scoped into a verified 4-page submission document. Then the engineering work came roaring back — the long-open LCD power issue got resolved, the obstacle-detection sensor-fusion idea from Week 11 actually got built, a recognition-threshold bug got fixed, and the full autonomous pipeline drove and turned the real robot for the first time. Getting the turn clean took two more rounds: a clearance-distance fix, then an overshoot investigation that traced the real cause to perception latency, and a voltage-sag lead that turned out to be a genuinely dead battery cell. The week closed with a big push: turning parked as an accepted hardware limit, forward/backward person-following and camera tilt control coming online, a full medicine reminder system with RFID and keypad acknowledge, and a robot clock in the web UI that surfaced a real timezone bug. This post is still in progress and will be filled in further as the week continues.

What the Structural Read Found

Every heading level of the Thesis Report was reviewed to separate three genuinely different problems that "the report isn't finished" can mean:

  • Completely empty sections — Chapter 5's System Integration Evaluation, Objectives Achievement, and Limitations and Threats to Validity; all of Chapter 6; all six appendices, A through F.
  • False alarms — two sections in Chapter 4 still marked ***draft that, on closer read, turned out to already be complete. A labeling leftover, not a real gap.
  • Sections that are filled but now factually behind the actual project — Hardware Implementation's I2C-bus description (predates the bit-banged LCD driver fix), GSM Integration ending on "procured" rather than describing the SMS system now confirmed working, Individual Feature Results covering only 2 of the 15 features, and Phase 1's exclusion list still claiming GSM and live fall-detection weren't done — both now are.

Splitting the problem this way matters because each category needs a different fix: the false alarms just need their draft flag removed, the stale sections need updating to match reality rather than being rewritten from scratch, and the empty sections need real content written for the first time.

A Draft-Fill Reference Guide, Grounded in the Real Project History

For every gap found, a reference page (thesis_fill_guide.html — a local scratch file, not part of this repo) was put together with copy-paste-ready draft text for each section, written to match the report's existing academic tone rather than as placeholder filler. Grounded in what actually happened on this project: the RFID and LCD hardware-fault diagnoses, the SIM800L-to-A76xx GSM migration, motor torque sizing, the person-tracker/fall-detection lock-state gating, and keypad-plus-web patient enrollment — the same history this blog has been tracking week by week.

Deliberately left for the user to write personally, not drafted: the Ethics Approval appendix, the Final Reflection section, and the wiring-diagram appendix — these need to be the author's own material, not generated on their behalf.

A Full LaTeX Version of the Dissertation

A parallel LaTeX build of the whole dissertation went in under reports/LaTex Report/, mirroring the folder layout of an earlier coursework report (main.tex + sections/ + code/ + images/ + references.bib). Every section was populated from the real, freshly re-extracted Thesis Report content — every paragraph and all 7 tables — not placeholder text.

The whole document was then converted to \documentclass[journal,twocolumn]{IEEEtran} (originally a chapter-based report class), which meant shifting every heading level down one and fixing every "Chapter X" reference to "Section X" across all six section files. Getting IEEEtran's twocolumn layout to actually compile surfaced four separate issues: a MiKTeX font-expansion error (fixed by disabling microtype expansion), Unicode characters inside code listings breaking pdfLaTeX (fixed with a literate table), a wide table refusing to run in twocolumn mode (fixed by wrapping it in \onecolumn/\twocolumn), and \appendix (singular) silently dropping three of six appendices — the fix was the plural \appendices. The Declaration of Originality, Acknowledgements, Table of Contents, and all six appendices were then removed from this LaTeX version entirely, leaving Title/Abstract plus six numbered sections.

Re-Scoped to an 8-Page Submission Document

The same LaTeX report was then trimmed down to an 8-page-max submission: System Design and Implementation merged into one section, Related Work condensed to about four paragraphs plus one comparison table, and references.bib cut down to the 7 citations that could actually be verified as real — every placeholder citation dropped rather than left in. Two real figure slots were added (images/cara_robot.jpg, images/test_setup.jpg) that render automatically the moment those files exist — boxed placeholders until then, no `.tex` edit needed once the photos are dropped in.

Verified, not assumed: the true compiled page count was read directly from pdfLaTeX's own log line — an earlier log-grepping check had silently matched the wrong "page marker" text from an unrelated table-overflow warning. The real count: 4 pages, well inside the 8-page cap.

Docx Progress Check and a Corrected Power Diagram

The user's own edits to the Word version of the report were reviewed — the earlier fill-guide content for Chapter 5, Chapter 6, and the Chapter 4 corrections had already been pasted in. Checking which figures are genuinely embedded images (rather than just captions) confirmed Figures 3-1 and 3-2 are real, and re-catalogued what's still empty: the Physical Design section and all six appendices.

The power-system diagram above was built for that Physical Design section, alongside matching report prose — and corrected mid-session after it came out that the Jetson actually runs on 19V through a boost converter with a 2A fuse (wired by the user), not 5V as first assumed. The diagram's Jetson branch was relabeled from a flagged "buck, needs verification" box to the correct 19V boost path with the fuse drawn in. One FYI flagged, not treated as a blocker: that 2A fuse sits under the Jetson power adapter's rated 2.37A draw. Separately, a paragraph already pasted into the docx's Power System Design section turned out to be the pre-correction version — still describing "5V... 4A" — flagged for replacement, along with a garbled figure caption/number that needs a field refresh.

The LCD Mystery, Mostly Resolved — a Real Power Fix

The dark-LCD investigation from Week 11 ended with a physical fix: the whole robot now runs on unified single-battery power instead of the mixed external/converter setup that made the earlier tests hard to interpret, and the LCD is confirmed visually working again. It's not a fully closed loop, though — a settling delay was added to the isConnected() I2C ACK diagnostic to test a timing hypothesis for why it disagreed with the direct visual confirmation the display was working, and that disagreement did not get resolved. Documented honestly as still-unresolved rather than claimed fixed just because the display itself is working.

Obstacle-Detection Sensor Fusion, Actually Built

The diagonal-sensor idea designed but deliberately left unbuilt in Week 11 is real code now. frontBlocked()/backBlocked() replace the old flat "is either corner sensor close?" checks, cross-referencing each corner sensor's sin(45°)/cos(45°)-decomposed side-component against the true L/R sensors — exactly the sensor-fusion approach discussed but not built last week, now distinguishing "this is really a side wall" from "this is genuinely something ahead or behind," which a raw diagonal reading alone can't do. HARD_STOP_DIST (15cm) sits underneath as an unconditional safety floor — always blocks that close regardless of how the fusion interprets it, no exceptions. The fusion result was also added to the live status line for visibility while testing.

Full Autonomous Pipeline Verified Live — Including the Turn Itself

Getting there needed one more bug fixed first: the LBPH recognition confidence threshold was raised from 70 to 85 after live testing found a clean, correct face match scoring 78.66 — just above the old threshold, causing a false LOST/no-match on a genuinely good detection. It turned out to be a duplicate bug across two independent recognizer instances, since the ROS2 node and the web UI each keep their own.

With that fixed, the full autonomous tracking pipeline was live-verified end to end for real this time: real SET_SPEED/TURN_LEFT commands with correct proportional-speed deceleration actually reaching the Arduino — the "watched it turn to recenter" moment that's been open since Week 11 finally happened. A new standalone tool, wasd_web_control.py (a Flask WASD control page on port 5003), came out of this too, for bench-testing the L298N motor driver in isolation from the rest of the stack.

The "Robot Isn't Moving" Mystery — a Dead Battery

The long-open "robot not moving, no sound at all" report from Week 11 finally got root-caused: a dead battery, not a wiring or driver fault. Confirmed via an isolated bench test using the new WASD tool above, then cara_main_jetson.ino was re-flashed and re-verified back on the Arduino afterward. It came back a second time the next morning — the battery had simply died again overnight — root-caused the same way and cleared before continuing.

First Live Turn — a Clearance Fix, an Overshoot Investigation, and the Real Culprit

With the battery sorted, the full pipeline went up for real: camera_node → person_tracker_node → motion_controller_node (autonomous_enabled:=true) → arduino_bridge_node, plus two debug_viewer_node instances — one for face/patient tracking, one for skeleton/fall-detection (the second only publishes frames while a patient is actively locked, which briefly looked like a bug before being confirmed as correct, expected behaviour).

The first real turn attempt was rejected outright: BLOCKED:TURN_RIGHT. The cause was a threshold mismatch — TURN_LEFT/TURN_RIGHT were gating on the raw L/R ultrasonic sensor against the same 60cm STOP_DIST used for forward/backward driving clearance, reused as-is even though turning in place doesn't sweep nearly that much lateral space. Actual clearance in the test area was ~30–47cm — comfortably safe for a turn, just under the borrowed 60cm requirement. Fixed with a new, turn-specific TURN_STOP_DIST=20cm and an isTurnBlocked() check, per explicit instruction that "safe distance to stop should be maximum 15–20cm" — the frontBlocked()/backBlocked() fusion logic for actual driving was left untouched.

Turning then worked, but visibly overshot past center. Two hypotheses were tested in order, not guessed: first, motor coast-down — STOP was reusing the same gentle deceleration ramp as everything else, measured at ~624ms to fully stop, meaning the robot kept driving in the same direction for over half a second after STOP was logged. A separate, much steeper STOP_ACCEL_STEP=40 was added for stopping specifically (direction reversals still use the gentle ramp, to protect the H-bridge from an abrupt polarity flip) — verified live: SPD now reaches 0 within ~110ms of STOP, down from ~624ms.

Fixed, but not the real cause: the overshoot was reported just as bad after the deceleration fix. Log evidence — a TURN_RIGHT immediately followed by a TURN_LEFT correction burst — points to the actual dominant cause being perception latency, not motor physics: face detection is CPU-heavy (~300%+ on person_tracker_node), so by the time a "you're centered" frame is captured, processed, and turned into a STOP command, the robot has already kept turning for that whole delay window at real speed. The motor-stop fix is real and worth keeping, it just wasn't the dominant factor. Not yet fixed further — options on the table: lower the max turn speed so less real-world rotation happens per unit of latency, and/or have motion_controller_node start slowing before literal frame-center to anticipate the lag.

Torque Floor Raised — and a New Power Lead for Next Session

Live testing found the old MIN_TURN_SPEED=150 — and even speeds up to 224–238 tried during testing — produced audible jitter and buzzing with no actual movement, consistent with the already-known underpowered drive motors lacking breakaway torque below roughly 200 PWM. Raised to MIN_TURN_SPEED=200 so a turn never starts in that buzz-without-moving zone.

A more important finding came out of that same testing, still unresolved: even at 238 PWM, on the full unified-battery setup (Arduino, Jetson, sensors, and motors all sharing one battery), the motors reportedly still weren't moving — a real contrast with the isolated bench test earlier that moved fine at only 150–180 PWM on its own dedicated supply. The leading theory heading into next session is voltage sag: the unified battery/converter setup may not be able to supply enough current to the motors once everything else is also drawing from it under motor startup load, rather than a firmware or wiring fault. Next step is measuring actual voltage at the motor driver's input while a turn is commanded, and weighing whether the motor driver should go back onto its own dedicated supply — though the motors were already flagged underpowered and pending replacement before any of this, so that replacement may end up being the real fix regardless of how the power-sharing question resolves.

Process note for next time: a manual diagnostic command published directly to /cara/drive_cmd while motion_controller_node was still running got silently overridden by that node's own periodic STOP publish on the same topic. Any future direct-command probing needs to stop motion_controller_node first — a single publish doesn't just "win."

Power Split, Turning Parked as a Hardware Limit, Obstacle Fusion Proven Live

The voltage-sag lead from the previous section got a real answer: the 3S battery pack was confirmed genuinely faulty — one dead cell — not a firmware or power-sharing problem. The fix was a power split rather than a repair: the Jetson moved onto its own wall adapter, leaving the battery dedicated to the Arduino, motors, and sensors only.

Turning itself got parked rather than chased further in software: the overshoot and torque issues are a real hardware limit of the 6V DIY DC gear motors, not something more code can fix. That matches the motor replacement already flagged as pending back in Week 09 — it's the real fix, not another firmware patch.

The obstacle-fusion sensor logic built earlier this week finally got tested against real staged scenarios, not just traced through code: the hard-stop floor held in both directions against real MOVE_FORWARD commands, and side-wall corroboration worked correctly on both branches at once in a real room-corner test. One honest limitation surfaced too — a coincidental tolerance-match between a corner sensor and a true side sensor can explain away a genuine obstruction in tight corner geometries. Not a safety gap (HARD_STOP_DIST still catches it regardless), just a known limit of the heuristic. A submission deadline was also noted: 15 September 2026.

Speed Floor, Tighter Stop Distance, and a Live Mid-Drive Safety Check

Live testing pinned down the motors' real breakaway point: the entire 0–149 PWM range just jitters with no actual movement. MIN_DRIVE_SPEED=145 now floors the web UI's speed slider, and a matching START_SPEED_FLOOR=145 means a fresh MOVE_*/TURN_* from a stop jumps straight to 145 instead of climbing there gradually through the normal ramp.

STOP_DIST for forward/backward driving was tightened from 60cm to 20cm, matching TURN_STOP_DIST — the old 60cm was blocking MOVE_BACKWARD with a genuinely clear ~40cm behind the robot, and stop distance was capped at a maximum of 20cm per explicit instruction.

Real safety gap found and closed: obstacle checks (frontBlocked()/backBlocked()/turn-blocked) were only ever evaluated once, at the moment a command was accepted — never re-checked while the robot was already moving. A new checkLiveObstacles() now runs every loop() iteration, force-stopping immediately if the direction in motion becomes newly blocked. Live-verified: a real obstacle placed in front of the robot while driving at SPD:185 triggered an immediate EMERGENCY_STOP, decelerating to 0 in about a second.

Forward/Backward Follow, Faster Reversals, and Camera Tilt Comes Online

motion_controller_node now implements forward-follow using the tracked person's bounding-box area as a distance proxy. Live-calibrated by walking a real distance range, which turned up a real limitation: that area signal doesn't scale reliably up close — so the originally-planned MOVE_BACKWARD/retreat behavior was dropped entirely rather than trusted on an unreliable "stop at a safe distance" signal. Vision only decides when to approach; the Arduino's own tightened stop distance and live obstacle check (above) is what actually keeps it at a safe distance. Live-tested end to end, confirmed working.

Direction reversals now use the fast stop-deceleration to cancel the old direction first, not just a plain STOP — after live feedback that reacting to a person stepping aside mid-approach felt too slow. The ramp into the new direction is unchanged and still gentle, so this is fast to cancel and smooth to commit, with no new overshoot risk.

Camera tilt control (TILT_UP/TILT_DOWN/TILT_CENTER) came online too, repurposing the servo on pin 46 that had only ever done the one-shot greeting wave gesture before — kept continuously attached now, as its own actuator separate from the drive motors. Bench-tested over serial, all three commands acknowledge correctly, but the servo hasn't been visually confirmed actually moving yet, and it isn't wired into the web UI or the ROS2 tracking pipeline yet either (person_tracker_node already publishes the vertical position that would eventually drive it, unused so far). Separately, a reported turn "jitter" near a tracked person was investigated and confirmed live as the TURN_STOP_DIST safety check correctly detecting the person's own body — not a bug. Camera tilt is the intended fix for that close-range framing case, not a reason to weaken the safety check.

Naming correction: the tilt servo's firmware comments now consistently call it an MG90S, not the SG90 used elsewhere on this site and in earlier posts — worth reconciling once it's clear whether that's a part swap or just inconsistent naming.

A Full Medicine Reminder System

remote_control.py grew a complete reminder system: JSON storage (time, label, enabled, last-fired date), a 30-second background scheduler, REST endpoints for list/add/delete/test-now/acknowledge, and a UI panel in the main web interface. On the firmware side, triggerAlert() was generalized into triggerAlertWithMessage(), adding a MED_REMINDER:<label> path that reuses the same buzzer/forced-STOP/LCD mechanism as a real FALL_DETECTED.

Two more ways to acknowledge a reminder exist now, beyond the web UI: the keypad's 0 key enters a time-entry mode (type HHMM, # to confirm, * to cancel, with live digits shown on the LCD) to add one, and MFRC522 RFID reading was ported into the main firmware for the first time — tapping the patient's known tag now acknowledges an active alert, the same role the keypad's * already had. The serial reader watches the Arduino's STATE: line for an ALERT→OK transition, so the web notification clears no matter which path did the acknowledging. Both the RFID and keypad reminder-entry paths compiled clean and flashed, but haven't been physically tested yet — a real tag tap and keypad sequence is first on the list for next session.

Robot Clock in the Web UI — and a Timezone Bug It Surfaced

A new clock panel shows live time in the web UI, re-fetched every 5 seconds rather than ticking client-side, so it actually reveals real drift instead of just animating smoothly regardless of the truth. It's deliberately built on the Jetson's own system clock rather than the physical DS3231 RTC — that RTC shares the same hardware I2C bus as the damaged SCL=21 pin, so using it for real would mean writing a whole new bit-banged driver this close to the deadline. Confirmed with the project owner before choosing the simpler path over the "more correct" one.

Setting the time needs root, which the Flask process doesn't have — the adjust path attempts a non-interactive sudo and, if that fails, surfaces the exact one-time setup command needed (a visudo-validated sudoers line, not a raw edit, specifically to avoid the risk of a malformed file locking out sudo entirely).

Real bug found along the way: building this surfaced that the Jetson's timezone was set to Africa/Abidjan (GMT+0) instead of its actual location — looked up via IP geolocation rather than guessed, and corrected to Asia/Dubai. An already-running Python process caches its timezone at startup, so the fix needed a service restart before the web UI actually reflected it.

What Did Not Go Well (So Far)

The camera tilt servo isn't confirmed physically moving yet, despite acknowledging commands correctly — a real gap between "the firmware thinks it worked" and "it visibly worked." RFID and keypad reminder entry are flashed but physically untested. Turning is now a known, accepted hardware limit rather than a solved problem — the real fix is motor replacement, not more software. The isConnected() I2C diagnostic still disagrees with the LCD's actual working state. The physical wristband still hasn't been built, person_tracker_node still needs a restart to pick up a freshly trained model, and remote_control.py still isn't migrated onto /cara/drive_cmd. On the report side, the docx still has a stale pre-correction power paragraph sitting in it that needs manually replacing, and the Physical Design section plus all six appendices remain unwritten.
