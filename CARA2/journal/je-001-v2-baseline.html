Technical Report

CARA V2.0 Baseline: State of a Low-Cost Assistive Robot Platform at the Start of Independent Development

Jayashanka Anushan1

1 Independent researcher. Correspondence via the project repository.

Received 8 October 2026Published 8 October 2026Linked threads EXP-01, EXP-04

Abstract

CARA (Companion Assistive Robot for the Aged) is a sub-$500 mobile robot that monitors an older person living alone and alerts family by GSM SMS without depending on Wi-Fi. Its first version (V1) was built and evaluated in 2026; it is now continued as the author’s independent research platform (V2.0). This report fixes the starting baseline. It describes the two-tier hardware and software architecture (Arduino Mega 2560 for real-time control and alerting, NVIDIA Jetson Nano for perception), summarises the capabilities verified in V1 with their evidence, and characterises the faults found during integration — damaged microcontroller I/O, supply-dependent peripheral behaviour, a GSM supply margin of about 6.5 V, a locomotion torque limit, and process contention on shared devices. An audit of the inherited record also yields three corrections: the reported fall-detection accuracy (87.6 % test, 89.6 % cross-validated) belongs to the deployed 644-sample model, not to an older 95.7 % model trained on fewer samples; the final demonstration ran fall detection without the trained classifier; and the repository firmware may not match what is flashed on the robot. Nine research threads for V2.0 are registered, each with its motivating evidence.

Keywords — assistive robotics; elderly care; fall detection; GSM alerting; low-cost robots; embedded reliability; research baseline

Introduction

Falls are a leading cause of injury in older adults [3], and older people living alone in developing regions often have family working abroad who cannot check on them directly. Commercial companion and assistive robots are typically priced and designed for well-connected households [12]. CARA was designed against the opposite constraints: a component budget under $500, no dependence on Wi-Fi for the safety function, and operation by a non-technical user [1].

V1 produced a working, tested prototype and a public build record [2]. V2.0 continues the same robot as a self-directed research programme. Before new experiments change anything, this report records the platform exactly as inherited, so that every later result can be compared against a documented starting point. It also records problems found while auditing the V1 material, because a baseline that silently carries forward errors would undermine everything built on it.

Section 2 describes the platform; Section 3 lists verified capabilities; Section 4 characterises faults and deployment findings; Section 5 sets out corrections to the V1 record; Section 6 states the limitations of this baseline; Section 7 registers the V2.0 research agenda.

Platform Description

Architecture

CARA splits responsibilities across two computers. The Arduino Mega 2560 owns everything that must keep working if the AI computer fails: motor drive with obstacle checks, the keypad panic button, the buzzer and LCD, and SMS alerting through a SIMCom A7670C LTE Cat-1 module. The NVIDIA Jetson Nano runs perception and user-facing services and sends text commands (for example FALL_DETECTED, MOVE_FORWARD, MED_REMINDER:<label>) to the Mega over USB serial at 9600 baud.

Table 1 summarises the hardware. A full pin map is maintained on the site’s Hardware page. Perception and control software

Camera-based fall detection is well studied in fixed-camera and smart-home settings [4]–[6]; CARA runs it on board a low-cost mobile robot. Fall detection uses MediaPipe pose estimation [7], [8] to extract 33 body landmarks per frame. A RandomForest classifier [9] with 200 trees, trained on 69 features (normalised landmark coordinates, body angle, aspect ratio and mean visibility) from 644 labelled images, scores each pose; a temporal tracker confirms a fall only after the score rises over consecutive checks. Patient identification uses a Haar cascade detector [10] and an LBPH face recogniser [11] trained on photos captured through the keypad or dashboard; a coloured wrist band serves as a fallback target when the face is not visible.

Two software paths exist on the Jetson. A ROS2 package runs camera, tracker, fall-detection, motion-control and serial-bridge nodes. A Flask web dashboard provides live video, remote driving, enrolment, medication reminders and logs. The two cannot run together because each needs exclusive use of the serial port and camera; the final V1 configuration used the dashboard, into which autonomous following and fall detection were moved.

Alert logic

A confirmed fall (from the Jetson) or the keypad # button puts the Mega into an alert state: motors stop, the buzzer sounds, and SMS messages go to the family number — six messages ten seconds apart, then one every five minutes until someone acknowledges with the keypad * or an RFID tap. A medication reminder uses the same alert state but stops sending SMS after six messages five minutes apart while continuing to alert locally. In the current firmware a reminder shows the same LCD text as a fall, which is a known usability gap.

Characterised Faults and Deployment Findings

Damaged microcontroller I/O

Raw pin testing showed the Mega’s hardware I²C clock line (pin 21) stuck permanently low. Because the hardware I²C peripheral cannot be moved to other pins, the LCD driver was rewritten as a bit-banged I²C implementation on pins 20 and A0, and the real-time clock was later moved onto the same software bus at its own address. Hardware Serial1 (pins 18/19) gave no response to the GSM module after repeated reseating, while Serial2 worked immediately; Serial1 is treated as suspect rather than confirmed dead until it is retested in isolation.

Supply-dependent peripheral behaviour

Several peripherals behaved correctly in isolated bench tests and failed once the full system was running. Five of six ultrasonic sensors read a constant 0.00 cm while sharing the Arduino’s 5 V rail. The MFRC522 RFID reader returned its correct version register (0x92) and read tags in isolation, but returned 0x24 and detected nothing inside the full firmware. A seven-configuration isolation test traced RFID tag detection to the supply path: it fails when the Mega is powered through the Jetson’s USB port and works on a clean direct supply. This is recorded as a power-architecture requirement of the design rather than a component fault [13]. The firmware also re-initialises the reader whenever its version register looks wrong, as a software mitigation.

GSM supply margin

With the A7670C isolated on a bench supply, SMS reliability depended sharply on supply voltage (Table 3). Below about 6.5 V, AT commands arrived corrupted and the module occasionally lost network registration; at 6.5 V all six test messages were delivered. Results at 6.6–6.7 V are excluded because the SIM ran out of credit during that batch. On the assembled robot, intermittent single-byte corruption caused occasional send failures, which the firmware now handles by re-asserting text mode before every send and retrying up to three times.

Locomotion

The drive motors move the robot straight at 150 PWM but need about 220 PWM to turn in place, and one side stalls during turns under both open-loop and encoder-based closed-loop control. Because closed-loop control did not remove the stall, it is attributed to motor torque rather than control. With the motors running, about 60 % of serial status lines were corrupted in one trial, compared with none while stationary, which points to electrical noise or supply sag on the USB link.

Process contention and latency

Only one process can own the Arduino serial port and the camera. A dashboard service configured to restart automatically repeatedly reclaimed the camera from the ROS2 camera node, which corrupted its capture until the whole pipeline was restarted. Separately, the ROS2 middleware queued stale frames by default; limiting image subscriptions to the latest frame cut median camera-to-tracker latency from 710 ms to about 101 ms.

Presence sensing and an unsafe interaction

The rear PIR sensor was observed stuck HIGH for over 24 seconds with nobody present, so presence sensing was disabled and the robot now starts directly in its monitoring state. During the same period, a real safety fault was found: an autonomous approach behaviour resumed whenever a remote-control button was released, so the robot could drive off with no command given. It was fixed by latching manual control for the rest of the session once anyone drives from the web view.

Corrections to the V1 Record

Auditing the inherited material produced three points that change how V1 results should be read.

Which classifier the accuracy figures describe

The model directory holds two classifiers. The deployed model (644 samples) reports 87.6 % test and 89.6 % cross-validated accuracy; these are the figures reported for V1. An older file trained on 461 samples reports 95.7 % test and 90.0 % cross-validated accuracy, and is still loaded by two standalone test scripts. The higher figure comes from a smaller dataset and a different test split and should not be attributed to the deployed system.

The detection path used in the final demonstration

From 3 October 2026, fall detection ran inside the web dashboard process rather than the ROS2 node. That process logged that no trained classifier was found and fell back to a rule-based detector that judges a fall from hip and shoulder height in the frame. An attempt to crop detection to the patient’s region was reverted the same day because the fallback misread a cropped standing person as lying down. The classifier figures in Table 2 therefore describe the offline and ROS2 paths, not the final demonstration configuration.

Repository and robot may differ

Dashboard code comments dated 6 October 2026 describe a firmware software-clock fallback and an encoder-based stall guard, neither of which is present in the repository firmware. The firmware header also places the LED and servo on pins that contradict the 29 September wiring log. Until the flashed firmware is read back and compared (EXP-01), the repository cannot be assumed to reproduce the robot.

Consequence for V2.0No firmware is changed until robot and repository agree, and every V2.0 fall-detection result will state which detection path and which model produced it.

Limitations of this Baseline

  • The engineering record for 30 September – 7 October 2026 was reconstructed after the fact from dated code comments, file timestamps and dashboard logs, because no version-control history exists for those days.
  • Most V1 measurements come from a single indoor environment, one enrolled person and short trials; they show feasibility, not generalisable performance.
  • Several results (Table 2) were obtained on firmware variants that have since been consolidated and have not been repeated on the current firmware.
  • The battery pack’s composition is documented (custom 18650 pack, Samsung INR18650-32E cells, ~12 V), but its endurance under the current configuration has not been measured.

Conclusion

CARA enters V2.0 as a working but imperfect platform: fall alerts, SMS escalation, remote driving, reminders and following all run on the assembled robot, while power distribution, locomotion torque, damaged microcontroller I/O and process contention set clear limits. The audit behind this report also corrected how two headline V1 results should be read and found that the code repository may not exactly match the robot. Fixing that last point is the first V2.0 task, because every later experiment depends on knowing precisely what is being tested.
