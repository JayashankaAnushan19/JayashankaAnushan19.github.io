Architecture

How CARA is put together: what runs where, how the two computers talk, and what happens when an alert fires. Changes made during V2.0 are recorded in daily notes and reflected here.

Two-tier design

An Arduino Mega 2560 owns everything safety-critical and real-time: motor drive with obstacle checks, the keypad panic button, buzzer and LCD, and SMS alerting through a SIMCom A7670C LTE module. An alert can still go out if the AI computer crashes.

An NVIDIA Jetson Nano runs perception (camera, face recognition, pose-based fall detection), autonomous following, medication scheduling and the web dashboard. It sends short text commands to the Mega over USB serial at 9600 baud and reads back a status line about five times a second.

Serial protocol (Jetson → Mega)

CommandEffect on the Mega
FALL_DETECTEDStart a fall alert (see below). Repeats while already alerting just extend it.
MED_REMINDER:<label>Start a reminder alert, unless a fall alert is already active.
RESETClear any alert; return to monitoring.
MOVE_FORWARD · MOVE_BACKWARD · TURN_LEFT · TURN_RIGHT · STOPManual driving. Refused if an ultrasonic sensor in that direction reads ≤ 30 cm; forward speed ramps down from 70 cm.
MOVE_BACKWARD_SLOW · TURN_LEFT_SLOW · TURN_RIGHT_SLOWHalf-speed variants used only by autonomous following.
TILT_UP · TILT_DOWN · TILT_CENTERCamera tilt, 110–150° (servo unit currently failed).
SETTIME YYYY MM DD HH MM SSSet the real-time clock; the dashboard sends this after the GSM search finishes.

The dashboard also sends SET_SPEED: and SET_IPS:, which the current firmware ignores. Commands sent during the ~50–70 s GSM search at boot are discarded on purpose so they can’t all fire at once afterwards.

State machine and alert logic

The firmware has five states: idle, active, monitoring, alert and reset. Because the presence (PIR) sensors are disabled, the robot boots straight into monitoring and returns there after every alert; idle and active are currently never entered.
